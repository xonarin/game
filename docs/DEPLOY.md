# Как поднять Plant: локально и на продакшене

Инструкция пошаговая: выполняйте шаги по порядку, не пропуская. Если что-то пошло не так —
загляните в раздел [«Если что-то не работает»](#если-что-то-не-работает) в конце.

## Из чего состоит проект

Три отдельных репозитория, они работают вместе:

| Репозиторий | Что это | Порт локально |
|---|---|---|
| `game` (этот) | Сайт игры и API. **Единственный, кто работает с базой данных** | 3100 |
| [`plant-auth`](https://github.com/xonarin/plant-auth) | Сервис входа: через него входят и игроки, и админы (VK, Google, Steam, Telegram) | 3300 |
| [`plant-admin`](https://github.com/xonarin/plant-admin) | Админка | 3200 |

Важно понимать:
- У `plant-auth` и `plant-admin` **нет своей базы**. Всё, что им нужно, они спрашивают у игры.
- Поэтому **сначала всегда запускается игра**, потом вход, потом админка.
- Список сайтов, которым разрешено пользоваться входом («Домены»), хранится в базе игры.
  Пока он пуст — войти нельзя никуда (см. шаг «Разрешить сайтам вход»).

Подробно, как сервисы общаются между собой, — в [ARCHITECTURE.md](ARCHITECTURE.md).
Для запуска его читать не обязательно.

## Часть 1. Локальный запуск (для разработки)

### Шаг 1. Что нужно установить

- **Docker Desktop** — в нём работают все три сервиса, MySQL и Redis.
- **Git**.
- **Node.js 24** — только если хотите запускать проверки и сборку вне Docker.

Склонируйте три репозитория **в одну папку**, рядом друг с другом:

```bash
git clone https://github.com/xonarin/game.git
git clone https://github.com/xonarin/plant-auth.git
git clone https://github.com/xonarin/plant-admin.git
```

Должно получиться: `…/game`, `…/plant-auth`, `…/plant-admin`.

### Шаг 2. Запустить игру

Из папки `game`:

```bash
docker compose -f docker-compose.dev.yml up -d
```

Что произойдёт:
1. Поднимутся MySQL 8.4 и Redis 7.
2. MySQL **при самом первом запуске** создаст пустую базу `playtime` (пароль root — `dev`).
3. Контейнер игры установит зависимости (первый раз — несколько минут) и запустится.
4. Игра сама создаст в базе все таблицы. Ничего вручную создавать не нужно.

Следить за запуском:

```bash
docker logs -f game-app-1
```

Игра готова, когда в логе есть строки `[migrate] готово: …` и `The development server is running at …`.
Сайт: http://localhost:3100

> `.env` для локального запуска не обязателен: все секреты в dev берут одинаковые
> «учебные» значения во всех трёх сервисах, поэтому они сразу друг с другом согласованы.
> Если всё-таки создаёте `.env` (`cp .env.example .env`), то секреты в трёх репозиториях
> должны совпадать — таблица в Части 2, шаг 2.

### Шаг 3. Запустить сервис входа (plant-auth)

Из папки `plant-auth`:

```bash
docker compose up -d --build
```

Локальные настройки (dev-вход, адрес игры) он берёт из `docker-compose.override.yml`
автоматически. Проверка: http://localhost:3300/health должен ответить `{"ok":true}`.

### Шаг 4. Запустить админку (plant-admin)

Из папки `plant-admin`:

```bash
docker compose up -d --build
```

Админка: http://localhost:3200

### Шаг 5. Разрешить сайтам вход

Сейчас база пустая, и сервис входа никого не пускает: на любой попытке входа будет
«Источник не разрешён». Нужно один раз добавить разрешённые адреса.

Через админку этого не сделать — она сама требует входа. Поэтому — напрямую в базу
(MySQL Workbench или любой клиент: `localhost:3306`, пользователь `root`, пароль `dev`):

```sql
INSERT INTO playtime.AuthClient (origin, label, enabled, secret, createdAt, updatedAt) VALUES
  ('http://localhost:3100', 'Игра',           1, NULL, NOW(), NOW()),
  ('http://localhost:3200', 'Админка',        1, NULL, NOW(), NOW()),
  ('http://localhost:3201', 'Админка (Vite)', 1, NULL, NOW(), NOW());
```

- `secret = NULL` — в dev используется общий «учебный» секрет.
- **Исключение:** если в `.env` игры задан `GAME_VERIFY_SECRET`, то у строки игры в `secret`
  должно стоять **это же значение** (а если в `.env` админки задан `ADMIN_VERIFY_SECRET` —
  то же самое для строки админки). Иначе вход дойдёт до конца и упадёт на обмене кода.
- Сервис входа запоминает ответ на 30 секунд — подождите полминуты и пробуйте.

### Шаг 6. Сделать себя админом

1. Откройте http://localhost:3200, в поле dev-пользователя оставьте `admin` и нажмите **«Dev вход»**.
   Админка ответит «Этот аккаунт не является администратором» — так и должно быть:
   аккаунт создан, но он обычный.
2. Выдайте этому аккаунту роль админа:

   ```sql
   UPDATE playtime.User SET role = 'Admin' WHERE socialId = 'dev-admin';
   ```

   (Dev-пользователь с именем `X` получает `socialId = 'dev-X'`.)
3. Войдите в админку ещё раз — теперь пустит.

### Шаг 7. Загрузить каталог скинов

В админке: **«Каталог предметов» → «Запустить импорт сейчас»**. Займёт примерно минуту,
в каталоге появится около 20 800 предметов.

Дальше каталог обновляется сам по расписанию (по умолчанию понедельник 04:00 по Ташкенту,
меняется там же). Источник данных — настройка `catalog::sourceUrl` на странице «Настройки».

### Как начать с чистого листа

Удалить базу в Workbench **недостаточно**: MySQL создаёт базу `playtime` только при самом
первом запуске, на пустом хранилище. Если удалить только базу, игра не стартует с ошибкой
`Unknown database 'playtime'`.

Правильно — удалить хранилище целиком и запустить заново (из папки `game`):

```bash
docker compose -f docker-compose.dev.yml down -v
```

```bash
docker compose -f docker-compose.dev.yml up -d
```

**Внимание:** `-v` удаляет все данные MySQL и Redis игры. После этого снова шаги 5–7.

Если базу всё-таки удалили вручную — создайте пустую и перезапустите игру:

```sql
CREATE DATABASE playtime CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

```bash
docker restart game-app-1
```

## Часть 2. Продакшен: первый запуск

Ниже — запуск на чистом сервере с пустой базой.

### Шаг 1. Подготовить сервер и домены

Понадобятся:
- **Три домена** (примеры дальше по тексту):
  - `plant.cash` — игра;
  - `auth.plant.cash` — сервис входа;
  - `admin.plant.cash` — админка.
- **HTTPS** перед всеми тремя: Cloudflare Tunnel или nginx с сертификатом.
- **MySQL 8.4** и **Redis 7** (свои или в Docker).
- **Docker** на сервере.

### Шаг 2. Сгенерировать секреты

Каждый секрет — случайная строка. Сгенерировать:

```bash
openssl rand -hex 32
```

Некоторые секреты должны **совпадать** в разных сервисах. Сгенерируйте каждый **один раз**
и вставьте в оба места:

| Секрет | В игре (`game/.env`) | В другом сервисе | Зачем |
|---|---|---|---|
| A | `JWT_SECRET` | `GAME_JWT_SECRET` в plant-admin | админка ходит в игру от имени админа |
| B | `SERVICE_API_TOKEN` | `SERVICE_API_TOKEN` в plant-auth | сервис входа создаёт и находит игроков |
| C | `SYNC_HMAC_SECRET` | `SYNC_HMAC_SECRET` в plant-admin | админка загружает каталог |
| D | `ADMIN_SERVICE_TOKEN` | `ADMIN_SERVICE_TOKEN` в plant-admin | расписание и источник каталога без входа админа |
| E | `GAME_VERIFY_SECRET` | поле `secret` строки игры в «Доменах» (шаг 7) | вход в игру |
| F | — | `ADMIN_VERIFY_SECRET` в plant-admin и `secret` строки админки в «Доменах» (шаг 7) | вход в админку |

Запишите их в надёжное место (менеджер паролей). Никогда не коммитьте `.env` в git.

> Если раньше проект жил на другом сервере — старые ключи лежат в истории git и считаются
> скомпрометированными. Выпустите новые: FreeKassa (`FK_SECRET`, `FK_SECRET2`),
> FKWallet (`FK_API_KEY`), пароль MySQL, `JWT_SECRET`.

### Шаг 3. Создать базу данных

```sql
CREATE DATABASE playtime CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'playtime'@'%' IDENTIFIED BY '<пароль>';
GRANT ALL PRIVILEGES ON playtime.* TO 'playtime'@'%';
```

Кодировка `utf8mb4_unicode_ci` обязательна — именно в ней работают все таблицы.
**Таблицы создавать не нужно** — игра создаст их сама при первом запуске.

### Шаг 4. Запустить игру

1. Заполните `game/.env` по [`.env.example`](../.env.example). Обязательно:

   | Переменная | Значение |
   |---|---|
   | `NODE_ENV` | `production` |
   | `DATABASE_URL` | `mysql://playtime:<пароль>@<хост>:3306/playtime` |
   | `REDIS_URL` | `redis://<хост>:6379` |
   | `JWT_SECRET` | секрет A (не короче 32 символов, иначе игра не стартует) |
   | `PUBLIC_URL` | `https://plant.cash` |
   | `TRUST_PROXY` | `1` (см. ниже) |
   | `AUTH_SERVICE_URL` | `https://auth.plant.cash` — без него на странице входа не будет кнопок |
   | `AUTH_SERVICE_INTERNAL_URL` | внутренний адрес plant-auth, если игра видит его не по публичному домену |
   | `GAME_VERIFY_SECRET` | секрет E |
   | `SERVICE_API_TOKEN` | секрет B |
   | `SYNC_HMAC_SECRET` | секрет C |
   | `ADMIN_SERVICE_TOKEN` | секрет D |

   Необязательные: платежи (`FK_*`), Telegram-бонус (шаг 10), `CATALOG_SOURCE_HOSTS`.

2. Соберите и запустите (нужен Node.js 24 и yarn на машине сборки):

   ```bash
   yarn install --frozen-lockfile
   yarn build --release
   docker build -t plant .
   docker run -d --name plant --restart unless-stopped --env-file .env -p 3000:3000 plant
   ```

   Сайт и WebSocket работают на одном порту 3000 — на него и направьте HTTPS-прокси.

3. Проверьте лог:

   ```bash
   docker logs -f plant
   ```

   Должны быть строки `[migrate] готово: …` и `The server is running at …`. Если вместо этого `[config] …`
   или `[migrate] запуск остановлен` — в строке написана причина.

**Про `TRUST_PROXY`.** Защита от частых запросов считает посетителей по IP. За прокси
(Cloudflare, nginx) игра видит реальный IP, только если `TRUST_PROXY` задан правильно.
Иначе все посетители выглядят как один IP, и один злоумышленник может заблокировать всех.
- Один прокси перед игрой (Cloudflare Tunnel **или** nginx): `TRUST_PROXY=1`.
- Два подряд (Cloudflare → nginx → игра): `TRUST_PROXY=2`.
- Никогда не ставьте `true` — тогда IP можно подделать.

### Шаг 5. Запустить сервис входа (plant-auth)

1. В папке `plant-auth`: `cp .env.example .env` и заполните:

   | Переменная | Значение |
   |---|---|
   | `NODE_ENV` | `production` |
   | `AUTH_PUBLIC_URL` | `https://auth.plant.cash` |
   | `GAME_GRAPHQL_URL` | адрес игры, доступный из контейнера, + `/graphql` |
   | `SERVICE_API_TOKEN` | секрет B |
   | `TRUST_PROXY` | как у игры |
   | `DEV_LOGIN` | **пусто** (на продакшене dev-вход выключен) |

2. Настройте способы входа. Кнопка появляется, только если провайдер настроен:

   | Провайдер | Где создать | Что указать у провайдера | Переменные |
   |---|---|---|---|
   | VK ID | кабинет VK ID, веб-приложение | доверенный redirect: `https://auth.plant.cash/auth/vk/return` | `VKID_APP_ID` |
   | Google | [Google Cloud Console](https://console.cloud.google.com/apis/credentials), OAuth-клиент «Web application» | redirect URI: `https://auth.plant.cash/auth/google/return` | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |
   | Steam | [steamcommunity.com/dev/apikey](https://steamcommunity.com/dev/apikey) | домен `auth.plant.cash` | `STEAM_API_KEY` |
   | Telegram | бот в @BotFather | команда `/setdomain` → `auth.plant.cash` | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` |

   Старые игроки ВКонтакте сохраняют аккаунты: VK ID возвращает тот же ID пользователя.

3. Запустите (Redis для кодов входа поднимется вместе с ним):

   ```bash
   docker compose -f docker-compose.yml up -d --build
   ```

   Флаг `-f docker-compose.yml` нужен, чтобы **не** подхватился `docker-compose.override.yml`
   с dev-настройками.

4. Проверка: `https://auth.plant.cash/health` отвечает `{"ok":true}`.

### Шаг 6. Запустить админку (plant-admin)

1. В папке `plant-admin`: `cp .env.example .env` и заполните:

   | Переменная | Значение |
   |---|---|
   | `NODE_ENV` | `production` |
   | `ADMIN_PUBLIC_URL` | `https://admin.plant.cash` |
   | `AUTH_SERVICE_URL` | `https://auth.plant.cash` |
   | `AUTH_SERVICE_INTERNAL_URL` | внутренний адрес plant-auth (или тот же публичный) |
   | `ADMIN_VERIFY_SECRET` | секрет F |
   | `GAME_GRAPHQL_URL` | адрес игры, доступный из контейнера, + `/graphql` |
   | `GAME_JWT_SECRET` | секрет A |
   | `SYNC_HMAC_SECRET` | секрет C |
   | `ADMIN_SERVICE_TOKEN` | секрет D |
   | `TRUST_PROXY` | как у игры |

   Без `SYNC_HMAC_SECRET` и `ADMIN_SERVICE_TOKEN` админка работает, но импорт каталога
   и расписание не будут работать.

2. Запустите (тоже без dev-настроек):

   ```bash
   docker compose -f docker-compose.yml up -d --build
   ```

### Шаг 7. Разрешить сайтам вход

База пустая — сервис входа пока никого не пускает. Добавьте разрешённые адреса
(подставьте свои домены и секреты E и F из шага 2):

```sql
INSERT INTO playtime.AuthClient (origin, label, enabled, secret, createdAt, updatedAt) VALUES
  ('https://plant.cash',       'Игра',    1, '<секрет E>', NOW(), NOW()),
  ('https://admin.plant.cash', 'Админка', 1, '<секрет F>', NOW(), NOW());
```

- Адрес — точно как в браузере: со схемой `https://`, без `/` на конце, без пути.
- На продакшене `secret` **обязателен**: без него вход в этот сайт не пройдёт.
- Подождите 30 секунд (ответ кэшируется). Дальше домены можно менять в админке, раздел «Домены».

### Шаг 8. Назначить первого админа

1. Откройте `https://admin.plant.cash` и войдите любым способом.
   Админка ответит «Этот аккаунт не является администратором» — аккаунт создан, но он обычный.
2. Найдите свой аккаунт и выдайте роль:

   ```sql
   SELECT id, username, socialType, createdAt FROM playtime.User ORDER BY id DESC LIMIT 5;
   UPDATE playtime.User SET role = 'Admin' WHERE id = <ваш id>;
   ```

3. Войдите в админку ещё раз.

### Шаг 9. Загрузить каталог скинов

В админке: **«Каталог предметов» → «Запустить импорт сейчас»**, дождитесь «Готово».
Проверьте там же блок «Расписание автоимпорта»: должно быть «задача зарегистрирована».

### Шаг 10. Бонусы через Telegram (по желанию)

Бонус и промокоды требуют подписки на Telegram-канал и запуска бота. Без настройки бонусы
просто выключены.

1. Создайте бота в @BotFather, токен и имя — в `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` **игры**.
2. Добавьте бота **администратором** канала (иначе он не сможет проверять подписку).
   Канал — в `TELEGRAM_BONUS_CHANNEL`: числовой id вида `-1001234567890` или `@username`.
3. Задайте `TELEGRAM_WEBHOOK_SECRET` (случайная строка), перезапустите игру и один раз
   откройте в браузере:

   ```
   https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook?url=https://plant.cash/api/telegram/webhook&secret_token=<TELEGRAM_WEBHOOK_SECRET>
   ```

### Шаг 11. Проверить, что всё работает

- [ ] `https://plant.cash` открывается, вход игрока проходит.
- [ ] `https://admin.plant.cash` — вход проходит, видно «Дашборд».
- [ ] В «Каталоге скинов» около 20 800 предметов, расписание зарегистрировано.
- [ ] В логе игры нет ошибок: `docker logs plant --tail 100`.

## Часть 3. Как выкатить новую версию

1. Обновите код (`git pull`) в нужном репозитории.
2. Пересоберите и перезапустите:
   - **игра:** `yarn build --release`, `docker build -t plant .`, затем пересоздайте контейнер
     (`docker rm -f plant` и снова `docker run …` из шага 4);
   - **plant-auth / plant-admin:** `docker compose -f docker-compose.yml up -d --build`.
3. Если в игре появились новые миграции — они применятся **сами при старте**. Ничего
   выполнять руками не нужно. В логе будет `[migrate] … применено сейчас N`.

Порядок, если обновляются все три: игра → plant-auth → plant-admin.

## Часть 4. База данных: как устроена схема

### Что происходит при каждом старте игры

1. **Создаются недостающие таблицы** по описаниям в `src/data/models/` (`sequelize.sync()`).
   На пустой базе — все сразу. **Колонки существующих таблиц не меняются**, но недостающие индексы из модели добавляются (см. ниже, п. 4).
2. **Применяются новые миграции** из папки `migrations/` — по алфавиту, каждая один раз.
   Какие уже применены, записано в таблице `schema_migrations`.
3. **Создаются строки по умолчанию**, если их нет (например, расписание `catalog_import`).

Если миграция упала — игра **не запустится** и напишет в лог имя файла и ошибку MySQL.

### Как добавить или изменить поле

Например, нужно новое поле в таблице `Item`:

1. **Добавьте поле в модель** (`src/data/models/Item.ts`).
   Так оно появится на любой **новой** (пустой) базе.
2. **Добавьте миграцию** — новый файл `migrations/ГГГГ-ММ-ДД-описание.sql`.
   Так поле появится на **уже существующих** базах (у вас локально, на продакшене).
   Имя файла должно идти по алфавиту **после** всех существующих — проще всего начинать
   с сегодняшней даты.
3. **Миграция должна проверять, нет ли уже поля.** На новой базе поле уже создано на шаге 1
   старта, и простой `ALTER TABLE … ADD COLUMN` упадёт с ошибкой `Duplicate column` —
   игра не запустится. Шаблон:

   ```sql
   -- migrations/2026-11-20-item-float.sql: новое поле Item.float_value
   SET @sql = IF(
       EXISTS (SELECT 1 FROM information_schema.columns
               WHERE table_schema = DATABASE() AND table_name = 'Item' AND column_name = 'float_value'),
       'SELECT 1',
       'ALTER TABLE `Item` ADD COLUMN `float_value` DECIMAL(10,9) NULL'
   );
   PREPARE stmt FROM @sql;
   EXECUTE stmt;
   DEALLOCATE PREPARE stmt;
   ```

   Для индекса — то же самое, только проверка по `information_schema.statistics` (`index_name`).

4. **Индекс по новому полю — только в миграции, не в модели.** `sync()` не меняет колонки
   существующих таблиц, но **добавляет в них недостающие индексы** из модели. Колонки на этот
   момент ещё нет (её добавит миграция — она идёт после `sync()`), и старт падает. Поэтому такой
   индекс создаёт миграция (с проверкой, как выше), а в модели остаётся комментарий
   (пример — `idx_item_type_category` в `src/data/models/Item.ts`).

Правила:
- **Применённую миграцию не редактируют.** Игра заметит изменение файла и не запустится.
  Нужно что-то поправить — новым файлом. Если правка безобидная (комментарий), после проверки:
  `yarn migrate:rehash <файл>.sql`.
- **Имена таблиц чувствительны к регистру** (MySQL на Linux): `Item` и `item` — разные таблицы.
  Переименовали таблицу — поменяйте имя везде в коде (модель и ручной SQL в `src/data/repositories/`).
- Посмотреть состояние миграций: `yarn migrate:status`.

## Если что-то не работает

| Что видно | Почему | Что делать |
|---|---|---|
| «Не удалось войти. Источник не разрешён» | адреса сайта нет в «Доменах» (`AuthClient`) — например, после новой базы | Часть 1 шаг 5 / Часть 2 шаг 7, подождать 30 с |
| Вход дошёл до конца и упал на сайте | `secret` в «Доменах» не совпадает с `GAME_VERIFY_SECRET` / `ADMIN_VERIFY_SECRET` | сверить значения |
| Админка: «Этот аккаунт не является администратором» | у аккаунта нет роли Admin | Часть 1 шаг 6 / Часть 2 шаг 8 |
| Игра не стартует: `Unknown database 'playtime'` | базы нет (удалили вручную) | «Как начать с чистого листа» |
| Игра не стартует: `[migrate] … изменён` | отредактировали уже применённую миграцию | вернуть файл или `yarn migrate:rehash` |
| Игра не стартует: `Duplicate column` в миграции | миграция без проверки «есть ли поле» | Часть 4, шаблон |
| Импорт каталога: `INTERNAL: Внутренняя ошибка` | ошибка в игре — смотреть `docker logs`; например `Table … doesn't exist` | по тексту ошибки в логе игры |
| Импорт: «Не удалось получить ссылку на источник» | не совпадает `ADMIN_SERVICE_TOKEN` или неверная настройка `catalog::sourceUrl` | сверить токен / настройку |
| Импорт: ошибка подписи (`BAD_SIGNATURE`) | не совпадает `SYNC_HMAC_SECRET` | сверить секрет C |
| Все посетители блокируются лимитом разом | неверный `TRUST_PROXY` | Часть 2 шаг 4 |
